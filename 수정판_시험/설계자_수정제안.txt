설계자에게 — 디지골드 시험 결과와 수정 제안 (2026-10-12 밤)

[한 줄 요약]
hg2·hg3·hg4 는 끝까지 돌았지만, 이 롬(디지몬골드 v1.6 이지, IPKK)의 규칙이 설계 가정과 세 군데 달라서
전투 그림 읽기·전투 그림 섞는 방향·글자표(공백·문장부호) 가 맞지 않았다.
아래 수정(스크립트 2개 파일 몇 줄 + 표 파일 1개)을 스크립트 복사본에 적용해 hg2 → hg3 → hg4 → hg4_icons 를 처음부터 다시 돌렸다.
원본 hg*.py·design.json·NDS_*.tsv 는 고치지 않았고, 모두 프로그램으로 확인한 것이다(게임 화면으로 확인한 것은 아님 — 맨 아래 「폰 확인」).

[세 군데 달랐던 점]
1) 그림 읽기 — hg1.py ncgr_rows
   이 롬의 전투 그림 RGCN 1976개는 RAHC 「크기 칸」이 전부 0 이다(하트골드 원본 K 는 6432). ncgr_rows 가 이 칸으로 길이를 재서 0바이트 → 「size0」.
   → 1단계 front_sheet·back_sheet 가 빈 그림, 8단계 검산 222/222 실패. 게임은 이 칸을 안 보는 것으로 보인다(롬이 정상 동작).
   수정: px = data[c + 0x20:c + 0x20 + 6400]

2) 섞는 방향 — hg4.py (★ 가장 중요)
   원본 하트골드·디지골드의 전투 그림은 거의 전부 hg1 이름으로 'dp'(앞에서부터 풀기: 첫 암호 단어가 씨앗, 첫 평문 단어 = 0)다.
   hg4 의 encrypt_pt 는 끝에서부터('pt')로 섞어 넣어서, 게임이 원본 그림을 푸는 방식으로 새 그림을 풀면 잡음이 될 가능성이 높았다.
   (hg4 의 검산도 mode == 'pt' 를 정답으로 기대해서 크기 칸을 고쳐도 이 문제는 못 잡는다.)
   표본: 원본 앞모습의 투명(0번 색) 비율 — dp 로 풀면 0.59~0.88, pt 로 풀면 0.06~0.08.  처음 판의 새 그림은 반대(pt 0.65~0.85, dp 0.07).
   수정: encrypt_dp 추가(앞에서부터), 오른쪽 아래 대신 왼쪽 위 4픽셀을 투명으로, 검산을 mode == 'dp' 로.

3) 글자표 — NDS_글자표_추가.tsv (hg2·hg3 가 이미 읽는 자리. 월요일에 채우기로 한 표)
   - 공백: 이 롬 글에서 단어 사이는 {01DE}(308,243번, 예 「사진을{01DE}선택해」). hg1.detect_space 는 「한글 사이 비율 ≥ 0.3」 기준인데 실제 0.29 라 None 이 됐다
     (가장 흔한 한글 아닌 글자 비율 0.426 은 통과). → 이 때문에 hg2 도감 글 122건·hg3 장면 대사 일부가 공백에서 실패했다.
     detect_space 의 기준을 0.25 로 내려도 되고, 표에 직접 적어도 된다(아래 표는 후자).
   - 문장부호·숫자: 글 속 쓰임으로 확인한 번호 —
       {01AC} = ?   「어떻게 하겠습니까{01AC}」「괜찮겠습니까{01AC}」 (4,136번)
       {01AD} = ,   「여러분{01AD} 참가해 주세요」「버튼{01AD} 혹은 터치로」 (2,087번)
       {01AE} = .   「확인 중{01AE}{01AE}{01AE}」「입니다{01AE}」 (26,731번)
       {01AB} = !   「참가해 주세요{01AB}」 (16,306번)
       {01BE} = -   빈 이름 「-----」 (6,486번)
       {0121}~{012A} = 0~9   「{0122}{0121}만볼트」(=10만볼트), 「{0129}↵{0128}↵…」 (0=0121 … 9=012A)
     「…」 글자는 이 롬에 따로 없다({01AF} 0번). 점 세 개(...)로 쓴다 → 수정판 hg1.Charmap.enc 에서 … 를 ... 로 바꿔 넣게 했다(1줄).
   표는 같은 폴더의 NDS_글자표_추가.tsv (탭 구분, 첫 줄 「부호 / 글자」).
   남은 문장부호(따옴표·♂♀ 등)는 아직 확인 안 함 — hg3 보고에 나오면 같은 방법으로 추가.
